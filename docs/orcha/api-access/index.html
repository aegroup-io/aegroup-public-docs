Product API Access

The one way an agent talks to a product over HTTP. A standard-library Python SDK and JSON CLI that reaches DataVein or Orcha only through an explicit private profile — no logins, no discovered credentials, no improvised curl — and refuses to invent a success it cannot prove. Both harnesses reach products through it; neither gains authority from it.

Authentication, organization scope, route permission, and mutation authority are four separate gates. Passing one never implies another — an authenticated token is not organization authority, and a successful discovery is not an operator permission.

What it does

Exit 0 is success, 2 is a classified unavailable, partial, or denied result, 1 is invalid input. Every command emits exactly one JSON object.

Commands

  • my-harness api status — no profile, no credentials
  • profile --product datavein --environment dev — local readiness only; authorization explicitly not checked
  • discover — fixed reads of /version, /me, /orgs; at most three exchanges
  • request --input <absolute-json> — a cataloged read or, with apply:true, an authorized mutation
  • --include-data — payloads only on request, recursively redacted, treated as private data
  • --timeout — 15 s default, 60 s maximum, per exchange; no automatic retries

Profiles + credentials

An absolute, user-owned, non-symlink file opened once and used as a snapshot. It names the environment, an HTTPS-only origin, the expected principal and scope, allowed path prefixes, and a credential reference — never a literal secret.

Token URLs and scopes must match SHA-256 digests before any secret is sent. Nothing is discovered from repositories, .env files, browser state, or shell history; worker tokens are prohibited as providers. No browser, device-code, CLI, or web-session login — a missing credential is simply credential-unavailable.

Transport

HTTPS only. Environment proxies disabled. Every resolved address must be public; loopback, private, and link-local ranges are rejected. DNS is resolved once and the connection pinned to the checked address while TLS keeps the approved hostname. No redirect is ever followed — including at the token endpoint. Paths reject traversal, encoding tricks, and matrix parameters; JSON is bounded to 256 KiB with duplicate keys rejected.

Discovery + server contracts

A cataloged request requires the server to publish its environment, revision, and a digest-bound route catalog, and /me to prove principal type, scope, and permissions — an operations agent must be app-only with exactly the operations role. Missing or mismatched contracts return contract-mismatch, never an invented HTTP success. Every route entry, sub-contract, and body schema is digest-verified against server metadata.

Mutations

A mutation needs apply:true, a caller-supplied typed grant (environment, system, action, scope, authorization window — with expiry required), and a mutation plan whose digests bind the complete request and the exact route entry. Operation, correlation, and mutation headers must be echoed back or the disposition stays unknown. Nothing is retried automatically; an accepted response is reported as domain_outcome: unverified — downstream effects need independent proof.

What it does not claim

Profile readiness and successful discovery do not establish operations authority. The route-catalog envelope and operator-principal proofs are a proposed server contract, not a claim that every deployed product already serves them — and the client does not make those capabilities exist. In this release, DataVein run-now, retry, and replay actions and all state-changing transformation routes are deliberately unsupported until the server can prove a reviewed execution revision. A grant is caller evidence, not a server credential.
